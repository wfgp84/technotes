1TL;DR

Both are RAII wrappers around a mutex — lock in constructor, unlock in destructor. Difference is flexibility vs overhead.

Rule of thumb: use lock_guard (or scoped_lock in C++17+) by default; reach for unique_lock only when you need one of its extras — early unlock, condition variables, moving the lock out of scope, or timed / try locking.

2std::lock_guard — the minimalist

#include <mutex>

std::mutex m;
int counter = 0;

void increment() {
    std::lock_guard<std::mutex> lk(m);   // lock here
    ++counter;
}                                        // unlock here (dtor)
  • Locks on construction, unlocks on destruction. Period.
  • No .unlock() / .lock() API — can't release early.
  • Not movable — can't return it, can't store in a container.
  • Zero runtime overhead beyond calling lock()/unlock() on the mutex.

C++17 CTAD lets you drop the template argument

std::lock_guard lk(m);       // same as std::lock_guard<std::mutex> lk(m);

3std::unique_lock — the flexible one

std::mutex m;

void doWork() {
    std::unique_lock<std::mutex> lk(m);   // lock here
    // ... critical section ...

    lk.unlock();                       // release early
    doExpensiveWorkNotNeedingLock();

    lk.lock();                         // reacquire
    // ... more critical section ...
}                                        // dtor: unlock if still owned

Extras that lock_guard doesn't have

3.1   Deferred lock (deadlock-safe multi-lock)

std::mutex m1, m2;
std::unique_lock<std::mutex> lk1(m1, std::defer_lock);   // don't lock yet
std::unique_lock<std::mutex> lk2(m2, std::defer_lock);
std::lock(lk1, lk2);            // atomically locks both, deadlock-safe

3.2   Try-lock / timed lock

std::unique_lock<std::mutex> lk(m, std::try_to_lock);
if (lk.owns_lock()) {
    // got it
} else {
    // busy — do something else
}

// Timed mutex variant:
std::timed_mutex tm;
std::unique_lock<std::timed_mutex> lk(tm, std::chrono::milliseconds(50));
if (lk.owns_lock()) { /* got it within 50 ms */ }

3.3   Adopt an already-locked mutex

m.lock();
std::unique_lock<std::mutex> lk(m, std::adopt_lock);   // take ownership, don't lock again

3.4   Movable → can be returned from a function

std::unique_lock<std::mutex> getLock() {
    return std::unique_lock<std::mutex>(m);
}
auto lk = getLock();   // ownership moves out; lock_guard couldn't do this

4std::scoped_lock C++17 — usually the best default

std::mutex m1, m2;
std::scoped_lock lk(m1, m2);      // atomically locks BOTH, deadlock-safe
  • Takes any number of mutexes; locks them atomically via std::lock.
  • Same "no unlock early / not movable" restrictions as lock_guard.
  • Preferred replacement for lock_guard in C++17+ — it's a strict superset.
  • Also solves the classic 2-mutex deadlock trap in one line.
Why not always use scoped_lock? You still need unique_lock for condition variables, deferred / timed / try locks, or when the lock has to be moved.

5Why condition_variable needs unique_lock

This is often the deciding factor for picking unique_lock.
#include <condition_variable>
#include <mutex>

std::mutex m;
std::condition_variable cv;
bool ready = false;

void consumer() {
    std::unique_lock<std::mutex> lk(m);       // MUST be unique_lock
    cv.wait(lk, []{ return ready; });    // wait() calls lk.unlock() then lk.lock()
    // ready is now true, mutex re-acquired
}

condition_variable::wait needs to unlock the mutex while waiting and relock on wake — lock_guard doesn't expose those, so you must use unique_lock.

Note: std::condition_variable_any::wait works with any lock type, but plain std::condition_variable is faster and takes only unique_lock<mutex>.

6Decision flow

Need to lock N > 1 mutexes together? → std::scoped_lock C++17 Need condition_variable::wait? → std::unique_lock Need to unlock/relock inside the scope? → std::unique_lock Need try_lock / timed_lock via RAII? → std::unique_lock Need to move / return the lock? → std::unique_lock Otherwise (95% of cases) → std::lock_guard (or std::scoped_lock in C++17)

7Performance

Both wrap the same mutex operations, so the mutex itself dominates the cost. unique_lock adds ~1 extra bool for the "owns lock" state and a couple of branches in the destructor to check ownership — utterly negligible in almost all real code.

If you're on a truly critical hot path, lock_guard/scoped_lock do slightly less work in the destructor (they always unlock, no state to check), but you won't measure it unless you're inside a tight microbenchmark.

Wrappersizeof (typical, 64-bit)dtor branches
lock_guard<mutex>8 B (1 ptr)always unlock
scoped_lock<mutex>8 B (per mutex)always unlock
unique_lock<mutex>16 B (1 ptr + owns bool + padding)check owns_lock(), then unlock

8Common pitfalls

8.1   Unnamed lock — unlocks immediately!

std::lock_guard<std::mutex>(m);         // TEMPORARY! unlocks at end of expression
std::lock_guard<std::mutex> lk(m);      // ✓ named — unlocks at end of scope
This is the #1 threading bug in code reviews. Compilers with -Wall warn about it (-Wunused-value), but not always. Always name the variable.

8.2   Locking the same mutex twice on one thread — deadlock

std::mutex m;
void outer() {
    std::lock_guard<std::mutex> lk(m);
    inner();                         // inner() also locks m → DEADLOCK
}

Use std::recursive_mutex if you really need re-entrancy (rarely a good idea — usually a sign of design confusion).

8.3   Deadlock from lock order

// Thread A
std::lock_guard lk1(m1);
std::lock_guard lk2(m2);          // order: m1, m2

// Thread B
std::lock_guard lk1(m2);
std::lock_guard lk2(m1);          // order: m2, m1 → DEADLOCK when interleaved

Fix: use std::scoped_lock(m1, m2) or std::lock(lk1, lk2) with deferred locks. Both lock all mutexes atomically, in a deadlock-safe order.

8.4   Using lock_guard with condition_variable

std::lock_guard<std::mutex> lk(m);
cv.wait(lk, []{ return ready; });   // COMPILE ERROR: needs unique_lock

8.5   Calling .unlock() on a unique_lock you don't own

std::unique_lock<std::mutex> lk(m, std::defer_lock);
lk.unlock();                     // throws std::system_error

Use lk.owns_lock() to check ownership first, or design so it's obvious.

8.6   Holding a lock across I/O or long work

Lock only the smallest necessary region. If you need to release during I/O:

std::unique_lock<std::mutex> lk(m);
auto snapshot = shared_data;
lk.unlock();                     // release before I/O
writeToDisk(snapshot);
// don't relock unless you need to update shared state

9Full runnable example — producer / consumer

Shows lock_guard for short critical sections, unique_lock for cv.wait plus unlock-during-I/O.
#include <chrono>
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>

std::mutex m;
std::condition_variable cv;
std::queue<int> q;
bool done = false;

void producer() {
    for (int i = 0; i < 5; ++i) {
        {
            std::lock_guard<std::mutex> lk(m);           // simple scoped lock
            q.push(i);
            std::cout << "pushed " << i << "\n";
        }
        cv.notify_one();
        std::this_thread::sleep_for(std::chrono::milliseconds(100));
    }
    {
        std::lock_guard<std::mutex> lk(m);
        done = true;
    }
    cv.notify_all();
}

void consumer() {
    while (true) {
        std::unique_lock<std::mutex> lk(m);              // needed for cv.wait
        cv.wait(lk, []{ return !q.empty() || done; });
        while (!q.empty()) {
            int v = q.front(); q.pop();
            lk.unlock();                                // release before I/O
            std::cout << "  consumed " << v << "\n";
            lk.lock();                                  // reacquire
        }
        if (done) break;
    }
}

int main() {
    std::thread p(producer), c(consumer);
    p.join(); c.join();
}

10Related primitives

SinceTypePurpose
C++11 std::mutex Basic mutual exclusion.

C++14 std::shared_timed_mutex Reader/writer lock (timed). Multiple readers, one writer.
C++17 std::shared_mutex Reader/writer lock (untimed, faster).

Reader/writer example: 
std::shared_mutex sm;

// many readers, no writers:
std::shared_lock lk(sm);                // C++17

// exclusive writer:
std::unique_lock lk(sm);                // C++11
shared_lock takes shared ownership; unique_lock takes exclusive ownership on the same mutex.
