1TL;DR

ExecutionService is the façade that lets application code fire off work on a background thread pool and receive the completion callback back on the main (dispatcher) thread — so user code never has to worry about locking around the result.
  • Public API: schedule(Task) → OperationId and cancel(OperationId) → bool.
  • Split of work: Task::onExecution() runs on a worker thread; Task::onCompletion(status) runs on the main thread.
  • Wiring: composed of three collaborators — IExecutor (thread pool), ITaskCompletionHandler (bridge), and a Dispatcher (SIC message bus).
  • Ownership: ExecutionService owns the executor and completion handler via unique_ptr; the dispatcher is externally owned and held as DispatcherPtr.
  • Shutdown is deterministic: destructor calls shutdown() → cancelAll() + stop(), joining all workers.
Why not just std::async? Because completions from std::async fire on some worker thread and would force every user callback to be thread-safe. ExecutionService uses a SIC (Signal / Inter-Component) notification to route the completion back to the main event loop, giving you free single-threaded semantics for the result handler.

4Responsibilities per class

Class Kind Responsibility
IExecutionService interface Public façade: schedule / cancel. Only thing the application should depend on.
ExecutionService impl Assembles the collaborators, subscribes to the dispatcher, and forwards messages back to TaskCompletionHandler::complete.
IExecutor / Executor interface threaded Thread pool + pending queue + serving map. Owns worker threads and lifecycle (start/stop).
ITaskCompletionHandler / TaskCompletionHandler interface impl Bridges worker → main thread using a SIC signal. Holds completed tasks in completingTaskStorage_ until the main thread picks them up.
Task abstract User-supplied unit of work. Split into onExecution() (worker thread) and onCompletion(status) (main thread).
Operation value Task + state + status envelope handed around inside the subsystem. Users never see it.
TaskStatus DTO Exception carrier. Convertible to bool: true means the task threw.
TaskState enum PENDING → RUNNING → FINISHED, with CANCELED as a terminal branch.
OperationId alias typedef std::size_t. Returned by schedule(); the only handle the user gets.

Cancellation

cancel(opId) is a straight delegation to Executor::cancel. Only pending operations can be cancelled — if the operation is already RUNNING, the state transition RUNNING → CANCELED is forbidden and cancel() returns false.

Data-passing rule: the header documents that Task should receive its inputs by move or copy. Passing raw pointers/references from the main thread into an onExecution that reads them concurrently is your problem, not the service's.

Fig. 4 — Task state transitions. RUNNING → CANCELED and CANCELED → RUNNING are explicitly forbidden.
  • A thrown exception in onExecution() is captured into TaskStatus; the task still transitions to FINISHED and onCompletion() is still called — with status converting to true.
  • Cancellation is a one-way, best-effort operation. If the worker has already picked up the operation, cancel() returns false.

9Concurrency internals

Executor storage

class Executor : public IExecutor {
    // producer (main) ↔ consumer (workers), MPMC-safe:
    ConcurrentQueue<OperationPtr>                pendingOperations_;

    // id → running operation, guarded by mutex:
    std::map<OperationId, OperationPtr>          servingOperations_;
    mutable std::recursive_mutex               servingOperationsMutex_;

    detail::ExecutorWorkerPool                   pool_;
};
  • pendingOperations_: FIFO of enqueued but not-yet-picked-up operations. A worker calls dequeue(), moves the operation into servingOperations_, then executes.
  • servingOperations_: id-indexed so completed(id) can drop the entry cheaply on the main thread.
  • The mutex is recursive to allow the same worker to touch the map twice inside one operation lifecycle without deadlocking itself.

Operation state

struct Operation::AtomicState {
    mutable std::mutex stateMutex_;
    TaskState           state_;

    TaskState get() const;
    bool      swap(TaskState& other);   // enforces legal transitions
};

swap() is the only mutator — it rejects the two illegal transitions (RUNNING ⇆ CANCELED) atomically, which is what makes cancel(opId) race-free against a worker that just picked up the operation.

Completion storage

class TaskCompletionHandler : public ITaskCompletionHandler {
    struct ExecutedTask {
        TaskIntrusivePtr task;
        TaskStatus       status;
        OperationId      operationId;
    };

    std::map<TaskHashValue, ExecutedTask>  completingTaskStorage_;
    mutable std::recursive_mutex          storageMutex_;
};

The worker thread parks the finished ExecutedTask in the map keyed by a hash, then fires a SIC TaskNotification carrying only that hash. The main thread looks the entry up in complete(), calls Task::onCompletion, and erases it. The hash keeps the notification message tiny (fits an std::size_t).

10Pitfalls & notes

Don't destroy an ExecutionService from inside a Task::onCompletion. Destruction calls shutdown() which stops the pool and touches the same TaskCompletionHandler that's currently running you. Route service teardown through a subsequent dispatcher tick.
Cancellation is best-effort. Once a worker has moved the operation from pendingOperations_ into servingOperations_, cancel() returns false. If your task must be interruptible, poll a cooperative flag inside onExecution().
Shared state passed by pointer/reference is on you. The interface documents that tasks should receive their data by move/copy. If you must share, add your own mutex.
Testing tip. Use ExecutionServiceMock (see include/oam/mocks/ExecutionServiceMock.h) to substitute a synchronous stub in tests — the interface-based design was put there for exactly this.
