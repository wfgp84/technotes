1Sorting a vector

Header <algorithm>. Range is [begin, end). Comparator must impose a strict weak ordering (use <, not <=).

Ascending

#include <algorithm>
#include <vector>

std::vector<int> v = {5, 2, 8, 1, 9, 3};
std::sort(v.begin(), v.end());          // 1 2 3 5 8 9

Descending

std::sort(v.begin(), v.end(), std::greater<int>());
// or with a lambda:
std::sort(v.begin(), v.end(), [](int a, int b) { return a > b; });

Custom comparator (structs)

struct Trade { std::string pair; double pnl; };
std::vector<Trade> trades = /* … */;

std::sort(trades.begin(), trades.end(),
          [](const Trade& a, const Trade& b) { return a.pnl > b.pnl; });

Related helpers

  • std::partial_sort(begin, middle, end) — sorts the first middle-begin smallest.
  • std::nth_element(begin, nth, end) — O(N) average; puts the nth-order element in position.
  • std::is_sorted(begin, end) — check ordering.
  • C++20 std::ranges::sort(v); and std::ranges::sort(v, std::greater{});
  • C++17 std::sort(std::execution::par, v.begin(), v.end()); — parallel (needs <execution>).

2Merging / concatenating vectors

Five common patterns depending on inputs (sorted vs unsorted, dedup, in-place).

2.1   Append (concatenate)

std::vector<int> a = {1, 2, 3}, b = {4, 5, 6};
a.insert(a.end(), b.begin(), b.end());       // a = {1,2,3,4,5,6}

Move elements out of b:

a.insert(a.end(),
         std::make_move_iterator(b.begin()),
         std::make_move_iterator(b.end()));

2.2   Merge two sorted → new sorted

std::vector<int> a = {1, 3, 5, 7};
std::vector<int> b = {2, 4, 6, 8};
std::vector<int> merged;
merged.reserve(a.size() + b.size());

std::merge(a.begin(), a.end(),
           b.begin(), b.end(),
           std::back_inserter(merged));           // stable, O(N+M)

2.3   In-place merge (single vector, two sorted halves)

std::vector<int> v = {1, 3, 5, 7, 2, 4, 6, 8};
auto mid = v.begin() + 4;
std::inplace_merge(v.begin(), mid, v.end());        // {1..8}

2.4   Concat then sort (unsorted inputs)

a.insert(a.end(), b.begin(), b.end());
std::sort(a.begin(), a.end());

2.5   Deduplicated union

std::vector<int> a = {1, 2, 3, 5};
std::vector<int> b = {2, 3, 4, 6};
std::vector<int> u;
u.reserve(a.size() + b.size());

std::set_union(a.begin(), a.end(),
               b.begin(), b.end(),
               std::back_inserter(u));               // {1,2,3,4,5,6}

Related: set_intersection, set_difference, set_symmetric_difference.

Decision matrix

3push_back vs emplace_back

Given std::vector<std::string> result; and std::string a("aa");

Behaviour summary

CallWhat happensExtra temp?CopiesMoves
result.push_back(a)Copy a into vector–10
result.push_back(std::move(a))Move a into vector–01
result.push_back("aa")Build temp std::string("aa"), then move✓01
result.emplace_back(a)Copy — same as push_back(a)–10
result.emplace_back(std::move(a))Move — same as push_back(std::move(a))–01
result.emplace_back("aa")Construct in place with string(const char*)✗00
result.emplace_back(2, 'a')Construct in place with string(size_t, char)✗00
Core difference: push_back(x) requires x to be a fully-built element (or something convertible to it) — it takes copy/move refs. emplace_back(args...) forwards its arguments directly to the element's constructor, building it in place. So emplace_back wins when you have raw constructor args, not an already-built object.

When emplace_back is strictly better

  1. Passing constructor arguments (no temporary) — e.g. emplace_back("aa"), emplace_back(2,'a').
  2. explicit constructors: push_back({1,2}) won't compile if the ctor is explicit; emplace_back(1,2) works.
  3. Move-only types you construct on the spot: v.emplace_back(new Foo) vs v.push_back(std::make_unique<Foo>()).

When push_back is preferable

  • Braced initializer lists: vv.push_back({1,2,3}) works; emplace_back({1,2,3}) can't deduce.
  • Readability — you already have an object; push_back(a) is clearer.
  • Type safety — you don't want to accidentally match some other constructor overload.
Misconception: "emplace_back is always faster." — Not true. If you already hold a std::string, emplace_back(a) and push_back(a) compile to identical code. The difference only shows up when you pass ctor args.

Traced demo

#include <iostream>
#include <string>
#include <vector>

struct Traced {
    std::string s;
    Traced(const char* p)      : s(p)              { std::cout << "  ctor(const char*)\n"; }
    Traced(size_t n, char c)   : s(n, c)           { std::cout << "  ctor(n, char)\n"; }
    Traced(const Traced& o)     : s(o.s)            { std::cout << "  copy\n"; }
    Traced(Traced&& o) noexcept : s(std::move(o.s)) { std::cout << "  move\n"; }
};

int main() {
    std::vector<Traced> v;
    v.reserve(10);                       // avoid reallocation noise

    Traced a("aa");                       // ctor(const char*)

    std::cout << "push_back(a):\n";         v.push_back(a);
    std::cout << "push_back(move a):\n";    v.push_back(std::move(a));
    std::cout << "push_back(\"aa\"):\n";      v.push_back("aa");
    std::cout << "emplace_back(\"aa\"):\n";   v.emplace_back("aa");
    std::cout << "emplace_back(2,'a'):\n";   v.emplace_back(2, 'a');
}

  copy
push_back(move a):
  move
push_back("aa"):
  ctor(const char*)
  move
emplace_back("aa"):
  ctor(const char*)         <- no move!
emplace_back(2,'a'):
  ctor(n, char)             <- no move!

4Which is faster?

Fastest to slowest for inserting "aa" into std::vector<std::string>.
RankCallOpsNotes
🥇FAST emplace_back("aa") · emplace_back(2,'a') 1 construction in place No temp, no move.
🥈 push_back(std::move(a)) 1 move-construction Same as gold, but empties a.
🥉 push_back("aa") 1 ctor + 1 move Compiler builds a temp, then moves.
SLOW push_back(a) 1 copy Must duplicate character data.
But for "aa" specifically: the string fits in SSO (Small String Optimization ~15-22 chars). No heap allocation happens; copy and move both just memcpy the 24-32 byte object. All five forms are within nanoseconds — you won't measure a difference for 2-char strings. The ranking really matters for long strings, containers, maps and other heap-backed types.

Micro-benchmark you can run

#include <chrono>
#include <iostream>
#include <string>
#include <vector>

int main() {
    constexpr int N = 10'000'000;
    auto bench = [&](auto label, auto fn) {
        std::vector<std::string> v;
        v.reserve(N);
        auto t0 = std::chrono::steady_clock::now();
        for (int i = 0; i < N; ++i) fn(v);
        auto t1 = std::chrono::steady_clock::now();
        std::cout << label << ": "
                  << std::chrono::duration<double, std::milli>(t1 - t0).count()
                  << " ms\n";
    };

    bench("push_back(a)",        [](auto& v){ std::string a("aa"); v.push_back(a); });
    bench("push_back(move a)",   [](auto& v){ std::string a("aa"); v.push_back(std::move(a)); });
    bench("push_back(\"aa\")",     [](auto& v){ v.push_back("aa"); });
    bench("emplace_back(\"aa\")",  [](auto& v){ v.emplace_back("aa"); });
    bench("emplace_back(2,'a')",  [](auto& v){ v.emplace_back(2, 'a'); });
}
push_back(a)         ~180 ms
push_back(move a)    ~150 ms
push_back("aa")      ~155 ms
emplace_back("aa")   ~140 ms   <- fastest
emplace_back(2,'a')  ~140 ms   <- fastest
The real speed lever is reserve(). Without it, the vector reallocates several times as it grows, and every existing element is moved on every growth. Always call v.reserve(n) when you know the target size.

5Practical rules of thumb

  1. Always v.reserve(n) when you know the size upfront.
  2. You have raw ctor args → emplace_back(args...).
  3. You have an lvalue you no longer need → push_back(std::move(x)).
  4. You have an lvalue you still need → push_back(x) (the copy is unavoidable).
  5. For SSO strings, int, small trivially-copyable structs — pick what reads best; the compiler will make them equivalent.
  6. Give move-constructors noexcept. If they're not, std::vector uses copy on reallocation (strong exception guarantee).
  7. Iterator invalidation on grow: after any operation that may reallocate (push_back, emplace_back, insert, resize), all previously held iterators/pointers/references are invalid.

6Applied example — sparse Jaccard similarity

Given a list of documents (each a vector of unique word IDs), output pairs with similarity > 0 as "i,j: 0.xxxx". Similarity = |A ∩ B| / |A ∪ B|. Because most pairs share nothing, avoid the naive O(N²) scan.

Algorithm

  1. Build an inverted index word → [doc_ids].
  2. For each word list, add +1 to intersect[(i, j)] for every unordered pair.
  3. For each pair with positive intersect, compute similarity from the sizes.
  4. Output sorted by (i, j) ascending.

C++ implementation

#include <vector>
#include <string>
#include <unordered_map>
#include <map>
#include <cstdio>

class Solution {
public:
    std::vector<std::string>
    computeSimilarities(std::vector<std::vector<int>>& docs) {
        std::unordered_map<int, std::vector<int>> inv;
        for (int i = 0; i < (int)docs.size(); ++i) {
            if (docs[i].empty()) continue;
            for (int w : docs[i]) inv[w].push_back(i);
        }

        std::map<std::pair<int,int>, int> inter;
        for (auto& kv : inv) {
            const auto& v = kv.second;
            for (size_t a = 0; a + 1 < v.size(); ++a)
                for (size_t b = a + 1; b < v.size(); ++b)
                    ++inter[{v[a], v[b]}];
        }

        std::vector<std::string> out;
        out.reserve(inter.size());
        for (auto& kv : inter) {
            int i = kv.first.first, j = kv.first.second, c = kv.second;
            double sim = (double)c / (docs[i].size() + docs[j].size() - c);
            char buf[64];
            std::snprintf(buf, sizeof(buf), "%d,%d: %.4f", i, j, sim);
            out.emplace_back(buf);          // <- emplace shines here
        }
        return out;
    }
};

Complexity

StageCost
Build inverted indexO(N · K)
Pairwise intersect countO(Σ f(w)²)   (small under sparsity)
Format outputO(P)   where P = pairs with sim > 0
Note the natural use of emplace_back(buf) at the last step — buf is a char*, and we want the vector to construct a std::string from it in place. This is exactly the case where emplace_back beats push_back(buf): one fewer move.
